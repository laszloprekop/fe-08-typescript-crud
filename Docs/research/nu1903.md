# NU1903 — SQLitePCLRaw.lib.e_sqlite3 2.1.11 (CVE-2025-6965)

**Ticket:** [#12](https://github.com/laszloprekop/fe-08-typescript-crud/issues/12) · **Resolved by running, 2026-07-17** · SDK 10.0.103

## TL;DR

- **CVE-2025-6965**, CVSS v4 **7.2 High**, CWE-197 (numeric truncation). Root cause: **SQLite < 3.50.2** — memory corruption when a query's aggregate-term count exceeds the available column count.
- **Not reachable from this app.** It issues no aggregate queries and lets no user shape SQL. See "Reachability".
- **A one-line pin fixes it anyway**, verified: `SQLitePCLRaw.lib.e_sqlite3` → `2.1.12`. Full CRUD still works; NU1903 clears.
- Recommendation: **fix *and* teach the reachability analysis.** Both, not either. (Question 4 — does it belong in a beginner exercise — left to the author; ticket stays open.)

## The advisory (primary source: GHSA-2m69-gcr7-jv3q)

| Field | Value |
|---|---|
| CVE | CVE-2025-6965 |
| Affected | `SQLitePCLRaw.lib.e_sqlite3` (and `.android`, `.ios`) **≤ 2.1.11** |
| Patched versions (GHSA field) | **"None"** |
| CVSS | 7.2 High (v4) |
| CWE | 197 numeric truncation |
| Root cause | SQLite before 3.50.2; aggregate terms can exceed column count → memory corruption |

**The "Patched versions: None" field is misleading and worth understanding.** It does *not* mean the vulnerability is unfixable. The affected range is `<= 2.1.11`, so any version **above** 2.1.11 is simply outside the range NuGet's NU1903 check compares against — the warning stops firing without GHSA ever populating a "patched" field. Verified below.

## Verified by running

### 1. The version chain — root cause confirmed

A throwaway console referencing `Microsoft.Data.Sqlite 10.0.10`, printing `select sqlite_version()`:

| SQLitePCLRaw.lib.e_sqlite3 | bundled SQLite | NU1903 |
|---|---|---|
| **2.1.11** (default transitive) | **3.49.1** | ⚠️ warns |
| **2.1.12** (pinned) | **3.53.3** | ✅ gone |

2.1.11 ships SQLite **3.49.1**, which is `< 3.50.2` — the advisory's root-cause mapping holds exactly.

**⚠️ Correction to an earlier lead on the ticket:** the guess that "SQLitePCLRaw 3.50.3 / 3.53.3 track SQLite's numbering" is **wrong**. `2.1.12` — a 2.x package — bundles SQLite **3.53.3**. The package version and the bundled-SQLite version are on different tracks. This is exactly why the fix had to be measured, not reasoned.

### 2. The pin works in the real (EF Core) project

Faithful copy of `api/` (EF Core Sqlite 10.0.10 + Swashbuckle 10.2.3) + one line:

```xml
<PackageReference Include="SQLitePCLRaw.lib.e_sqlite3" Version="2.1.12" />
```

- Build **succeeds**, NU1903 **gone**.
- Transitive resolve: `lib.e_sqlite3` → **2.1.12**; `bundle_e_sqlite3` and `provider.e_sqlite3` **stay 2.1.11** and that is fine — the advisory names only `lib.e_sqlite3` (the native library). **Lib-only pin is sufficient.**
- Ran on port 5231, own DB: GET (4 seeded) → **200**, POST → **201** (id 5), PUT → **204**, DELETE → **200**, final state correct. The pin breaks nothing.

The author's `api/cars.db` was never touched; all spikes used isolated DB files and non-5227 ports.

## Reachability — does it reach *this* app?

**No.** The vulnerable path is memory corruption triggered by a **query whose aggregate-term count exceeds the column count**. To reach it an attacker must influence the *structure* of a SQL query — specifically its aggregate terms.

This app cannot be made to do that:

- Every query is EF-generated: `ToListAsync` → `SELECT * FROM Cars`, `FindAsync(id)` → `SELECT … WHERE Id = @p LIMIT 1`, plus parameterised `INSERT`/`UPDATE`/`DELETE`. Confirmed from EF's own command log while running.
- **No aggregates anywhere** — no `GROUP BY`, no `COUNT`/`SUM`/etc., no `HAVING`.
- User input (brand/model/color/year) arrives only as **bound parameters** (`@p0…@p4`), never as query structure.
- The SQLite file is one the app creates and seeds itself — not an untrusted database opened from outside.

So the honest risk to this deployment is **effectively nil**. The warning is real; the exposure is not.

## Recommendation — fix *and* teach

Not "fix" vs "acknowledge" — **both**, because together they are a better lesson than either alone:

1. **Teach the reachability read first.** A high-severity warning appears; the professional move is not to panic-patch but to *read the advisory and assess whether it reaches you*. Here it doesn't, and the doc can show exactly why (no aggregate queries, no user-shaped SQL, self-created DB). That is a transferable skill worth more than the fix.
2. **Then pin it anyway**, and say why: a clean build (no red on `dotnet run`), defence-in-depth against future code that *might* add an aggregate query, and so the next person who clones the repo doesn't have to re-derive that it's safe. One line, verified non-breaking.

**Scope note for the author (this is the real open question, not the tech).** The pin edits `api/api.csproj`, and the map scoped `api/` to "validation and error shape only, not a rewrite." A dependency bump is neither — it is *maintenance*. Whether that fits a beginner exercise, and whether it belongs in doc 2's optional track or is just mentioned, is the author's call. The evidence says the fix is safe and trivial; the pedagogy is the decision.
